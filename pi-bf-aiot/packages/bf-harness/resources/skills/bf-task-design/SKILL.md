# 按任务设计

先读 `task_definition`、`task_state` 与 `summary`：当前候选、允许修改的文件、场景、验收条件、报告章节均以工具返回为准。字段与示例由 `task_schema` 提供。

- 参数分别记录来源和角色：用户、文献、测量是来源；硬约束、设计变量、假设是角色。硬约束绑定具体场景、设计字段或文件摘要；设计修改遵守 `design_space` 的文件范围、单位与上下界。
- 一个实际器件可以实现多个功能。共享器件只计一次体积、负载和能量。
- 先选择要回答的工程问题，再决定修改或实验。读取资料、加说明文字也应服务于这个问题。
- 初版按依赖形成候选；后续根据接口变化选择局部修订或联合修订。

单 Agent 任务的工具顺序：`task_commit` → `task_execute` → `validate` → `decide`。
`task_commit` 合并部分文件到完整父树。使用当前 revision 和 base_system。
执行器返回实际编译、求解与输入身份；独立检查返回本任务的结果。根据结果保留、修订或拒绝候选。
多专业任务使用本任务开放的 assign/commit/contract/integrate；角色数量由 profile 决定。

恢复先查询 `task_state`。`UNKNOWN` 等待操作对账；`COMPLETED_NOT_REGISTERED` 沿原 `task_execute` 登记已有结果。相同操作沿用 operation_id。相同输入的执行自动复用。改变要求后重做判定，改变设计后重做受影响执行。需求、模型或评价器变更由操作者建立新定义，原任务和结论保留。

接口沿“生成者→实际消费文件→执行器→检查器”核对。来源一致与工程性能是不同检查；下一次修订由实际性能结果决定。每轮公开说明问题、变化、执行结果、采用或修订理由。通过、失败和无法评价均可交付审查包；`ADOPT_PASSED` 只用于当前任务全部必需检查通过的候选。审查任务只读取与评价设计。

交付前用 `task_result(system_id)` 读取实际窗口电压、负载能量和来源；用 `path/offset/limit` 分页读取已有波形、事件或日志。功率使用对应电源轨，比例先统一单位，仿真值写为仿真结果。
交付时按 `task_schema` 的当前报告章节填写 `task_report`，每节引用当前文件或检查。随后 `release` 和 `close`。
报告说清任务目标、输入条件、实际修改、执行结果、采用决定和剩余工程问题。
