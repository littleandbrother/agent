# Controlled D-loop and H-loop protocol addendum

Status: prospective preparation only, 2026-10-01. No formal protocol is ratified, no participant/model call is dispatched, and no Agent efficacy, recursive improvement, hardware or product success is claimed.

## 1. Recovery and scope

The September 29 source recovered in `bf-paper-experiment-protocol-ledger.json` proposes E0–E7. Its 768 total combines heterogeneous units and is not a frozen sample size. Exact current model/provider revisions, reasoning/context settings, episode limits, total spending limit, split identities and statistical decisions remain unknown. The old Rotary/Pi implementation contains other model names and CNY/USD caps; those are historical, distinct ledgers, not implied magnetic-study authorization.

E0–E7 remain unchanged historical proposals. This addendum adds a separate prospective H study instead of retroactively calling design continuation, representation ablation, or an operator code repair a Harness self-improvement experiment. D means the engineered device/design. H means the program that designs or improves the designer, including declared solver P and improver U components. Candidate world models are separate from immutable reference reality.

## 2. D-loop core comparison

The first controlled comparison is strong generic coding Agent versus BF-Design. Additional domain-guided and matched-search arms from E1 may be added only in the frozen matrix. Both core arms get identical:

- Exact base model/provider/revision/fingerprint, reasoning, context, vision, temperature and seed policy
- Initial request, numeric facts, clarification answer sheet, public history, retrieval corpus/access, checkers, observation API and raw feedback
- Tools and permission to author code/tools, revise mechanics, circuit, firmware, architecture and cross-domain allocations; no fixed-architecture handicap for the generic arm
- Candidate/branch opportunities, public-verifier access, token/model/solver/verifier/CPU/wall-clock and monetary caps
- Parent commission, initial design state, task order or counterbalanced order assignment, and public final-selection rule

The declared difference is the method/representation implementation, pinned by intervention and Harness hashes. H is frozen within a D episode; in-task exploratory code is allowed equally and remains D work unless entered into the separate H protocol. A provider unable to execute an allowed architecture yields unsupported/model-extension status, not a physical failure. Restricting both methods to an executable subset requires an explicitly narrower task/claim, not silent provider-driven exclusion.

The primary endpoint is independently checked joint acceptance of the publicly selected final submission within the frozen resource budget. A hidden evaluator cannot choose a better historical candidate. Freeze all relevant submissions before revealing confirmation outcomes. Secondary endpoints include requirement preservation, unsupported assumptions, false completion, cost to public/independent acceptance and complete native artifact consistency. Mechanical/circuit/firmware local passes do not replace joint acceptance.

## 3. Additive H studies

### H-A1: participant-authored H0 → H1

1. Freeze H0, the immutable controller/kernel, model/tool interface, public development evidence, mutation scope and budget before generation
2. H0's designated improver is actually imported and invoked in a qualified fresh participant process; log its invocation and parent identity
3. The participant authors a source patch within allowed H files. Preserve the participant transcript, exact diff, original and final source, build output, attempts, costs and authorship. No-op, malformed, build failure, budget exhaustion and rejection are valid outcomes
4. An external builder produces and pins executable bytes. A trusted fresh-process launcher verifies and imports those exact bytes, then proves actual entrypoint invocation. A pre-import hash log, changed file timestamp, successful TypeScript build, or filename H1 alone is insufficient
5. Independent development qualification checks explanation/use, regressions, scope and safety without exposing sealed final holdouts. Candidate choice is fixed using public/qualification information only
6. Compare the preselected H1 and frozen H0 on previously unseen future parent commissions, using clean sessions without the originating conversation. The same independent evaluator and holdouts remain immutable and inaccessible to both

### H-A2: cost-matched frozen-H control

A frozen H0 branch receives the same total resource opportunity envelope as the evolved branch, not merely the same final solve cap. Count acquisition/history, H generation, build/repair, independent qualification, regression, transfer, rollback and future solving. Count failed candidates, rejected changes, discarded runs and human operations. Record any shared common acquisition cost and the preregistered allocation convention; show full incurred cost alongside attributed comparison cost. A frozen baseline may use its otherwise-unused allowance for ordinary generic search under a prespecified schedule. Do not invent synthetic baseline spending to make realized costs equal.

Primary H outcomes are future-task joint feasibility and cost/risk tradeoffs at equal total budget. Report method success at allocated caps and actual incurred cost separately. A costly benefit that never amortizes is not an amortized improvement. Choose repetitions and paired/clustered analysis after development variance work and before confirmation; do not stop at significance or selectively repeat failures.

### H-A3: later generation and recursive claim boundary

A later H1 → H2 generation must use the actually loaded H1 improvement procedure, receive only the preregistered public evidence and retain lineage to H0. If testing improved U, hold P and all other components fixed when comparing descendants generated by U0 and U1 under identical inputs/budgets. Freeze descendants before confirmation. A second patch produced by an outside engineer is external assistance, not a later participant generation. Merely running H1 on another design task is transfer, not recursive self-improvement.

Claims are staged: (a) participant-authored executable candidate, (b) actual fresh-process activation, (c) independent future-task benefit, (d) total-cost benefit, (e) replicated later-generation improvement. None follows automatically from the preceding software gate. No mandatory positive result: reject, restrict, rollback, stagnate or make no update when warranted.

## 4. Authority, qualification and rollback

Participants may edit D, their candidate world model, and the explicitly declared H sources. They cannot edit task facts, accepted energy/input boundaries, reference reality, evaluator/thresholds, hidden sets, evidence journal, budget settlement or promotion/rollback authority. World and task contracts come from the separate authoritative-world package and are bound by digest. Model/runtime/reference/budget unknown means blocked; source integrity or green fixture tests do not qualify physical truth or a sandbox.

The computational world freeze is not reference feasibility. A genuinely no-Agent, independently feasible reference under the same task/world is required before participants. An externally powered positive control, modified mission, dummy witness, undeclared precharge, stronger motion or old-model feasible row cannot satisfy this gate. Computation-only claims still require qualified computational reference evidence; physical claims additionally require measured/native evidence appropriate to them.

Rollback is externally controlled: preserve H0 and rejected candidate bytes, restore the exact prior source/build identities in a fresh process, and rerun the scoped deterministic checks. It does not erase costs or failures. Crash/unknown dispatch state requires reconciliation before retry; retries retain episode identity and billing effects, not new independent samples.

## 5. Negative controls and denominator

Required controls include no-op, build/import failure, stale build, pre-import-only activation log, hidden-feedback leak, evaluator mutation, overspend, omitted failed attempt, external manual fix, rollback, removal, clean-session transplant, out-of-scope use and broken generation lineage. These software controls test guards. They do not themselves show learned benefit or genuine participant autonomy.

Freeze an episode assignment registry before dispatch. Report every assigned episode, including invalid, exhausted, crashed, never-started, abstained and no-submission cases, plus every internal attempt and cost. Document scheduler failures separately without silently removing the all-assigned denominator. Cluster paraphrases and repeated conditions by parent commission. A scientific replicate is distinct from a retry of the same effect. Future H generation counts, D episode counts, solver calculations, manufactured specimens and physical operations are separate units.

User decisions, bundled into one exact prospective approval:

1. Freeze the intended task/mission facts (installation/envelope, external action/work, cold/warm starting state, weak-motion condition, receiver success/latency and permissible design boundary); accept or revise engineering-proposed values rather than guessing them
2. Select exact provider/model revision/configuration; approve per-episode and cumulative global resource/money caps, the existing ledger to use without reset, and execution window
3. Ratify the proposed split/matrix, repetitions/statistics, H mutation scope and total-budget allocation before any formal participant spending. The 768 proposal is not the default

Engineering must resolve without asking the user to do technical implementation:

- Bind the new authoritative world/task identities; qualify supported architecture freedom and a real no-Agent feasible witness. Preserve failure and legacy identities
- Obtain scoped numerical/native/reference evidence and independently freeze the evaluator, holdouts and leakage controls; all already inspected evidence remains development-exposed
- Run actual participant sandbox preflight on a supported authorized host. The current Linux host does not provide the existing macOS Seatbelt runtime; no fallback may silently remove isolation
- Adapt the existing executor's hardcoded model/ledger/task assumptions to the approved manifest, retain recovery accounting, add post-import/invocation load proof and source/build binding
- Run the scoped application/contract tests for the selected magnetic path. Unrelated STM32 deployment failures are documented, not made a universal prerequisite. Conversely, a failing magnetic evaluator/runtime gate cannot be waived by a large unrelated test pass count

A prospective owner approval cannot substitute for missing qualification, and an engineering pass cannot fabricate owner approval. This package intentionally offers no execute/dispatch action.
