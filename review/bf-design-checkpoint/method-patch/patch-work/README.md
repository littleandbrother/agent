# BF method offline patch

Date: 2026-10-01. This is a prospective source patch in an isolated scratch copy. It has not been committed, pushed, applied to the owner repository, or installed into the frozen integration evidence.

## What changed

- Four explicit profiles in the existing solver path: Strong Generic (R0Q0), BF-Design (R1Q1), representation-only (R1Q0), revision-only (R0Q1)
- Shared facts, requirements, feedback, tools, broad proposal permissions and two total candidate opportunities remain matched. BF-specific policy instructs functional/resource/condition relations, conflict attribution, parameter refinement and architecture recomposition; the other profiles independently omit R or Q procedures
- Prompt policy is executable source, not an arm label. The execution packet binds selected profile plus actual method/solver source and JS hashes. Runtime validates those against the frozen manifest
- A common bf_record_revision tool records actual before/after candidate hashes, observed run IDs, requested revision kind, rationale, falsifier and conditional relations. It distinguishes no-op, unverified artifact change and unsupported architecture proposal; no record declares evaluation or scientific acceptance
- Actual imports and solverPrompt invocation produce profile-bound receipt events; a separate supervisor verifies ordering, source/build bindings, output hash, PID, nonce, packet, clean fresh process and exit status. The auxiliary activation implementation is itself source/build-bound
- Capability admission is derived from the actual numeric-only provider. Both current magnetic tasks remain blocked for architecture and artifact-source support. Unknown component requirements, incomplete arm coverage and restricted baseline permissions fail closed. Selecting a real storage component also requires source support; it is not silently reduced to capacitance tuning
- All existing trusted-offline, zero-model, zero-native, qualification, authorization and independent-acceptance guards remain. Restored participant-writable state.json is newly rejected until a controller-owned checkpoint can authenticate history and cumulative opportunities

This bounded implementation has one revision round and two total candidate opportunities per episode. It does not promise unlimited rounds or implement live continuation. Prompt delivery, faithful action traces, design feasibility and method efficacy remain separate questions.

## Validation performed

Independent adversarial suite: **48 Node tests + 13 Python tests passed**.

Coverage includes profile mutation/drift, identical public facts across all four actual pure prompt invocations, source/build binding, forged observation/artifact metadata, used opportunities, no-op revisions, unsupported architecture, stale relation status, immutable receipts, unknown capability requirements, arm mismatch, source-required storage components, malformed process identities, pre-import/invocation-only/replayed/tampered receipts and Python supervisor readback of actual fresh inert Node process evidence.

These fresh processes imported and called only pure method/solver functions on explicitly synthetic test observations. They did not create a Pi SDK session, model participant, HTTP service or native scientific solver.

Four changed TypeScript files were syntax-transformed using Node's built-in type stripping, and the resulting JavaScript parsed. All changed Python files parsed. This is **not** a TypeScript project typecheck or a full Pi build.

The original 380-file package passed its portable integrity/trace verification again after the patch work. All old process evidence, tests, world/protocol inputs and seals remain untouched.

Commands, from this patch directory:
