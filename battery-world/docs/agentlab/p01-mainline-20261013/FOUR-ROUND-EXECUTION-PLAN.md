## 1. 目标与当前起点

四轮围绕同一个 P01 候选展开：先证明当前任务所需动作可执行，再清除严重使用摩擦，形成同版候选交付，最后提高设计质量。不要先分别建完所有软件、所有技能、所有研究功能，再尝试整链。

P01 首版范围沿用已有候选合同：在有来源的名义机械输入和声明初态下积能，按声明条件人工接通 MCU，建立连接，周期采样并完成 PC 解码，提交数字工程和检查证据。原始传感数据与气体浓度标定、人工接通与全自动启动、数字检查与实物验证分别记录。器件和策略由 BF 提出，不能在计划里预设最终设计答案。

现有八项数字检查范围保持：源模型适用域；原理图/BOM/引脚；PCB 连通性与 DRC；机械配合；固件事件逻辑；板级与固件接口；电源与实际负载链；交付版本。流程验证不修改这些要求，也不把失败改为通过。

## 2. 全过程的工作边界

1. P01 是唯一产品主线；其他九篇保留原会话、工程、费用和失败，不恢复施工。
2. 复用当前输入、环境和适用范围仍匹配的成功作业；不因组织四轮计划重跑旧仿真或旧目标构建。
3. 同一原生工程只有一个写入执行者；公共修复与 Pi 设计修改不并发。
4. 数据库查询仅 `mode=ro`，不创建查询用的第二个 Workbench，不清除 UNKNOWN、预留或账本，不更换 owner 绕过历史。
5. 不扩展 UI、不创建定时消息、不使用过时的 harness-creator、不新建一套候选状态系统。
6. 累计费用、token、请求数与运行时间授权不另设上限；但每个操作有有限范围，重复且无新证据的策略停止，等待报告与确认。
7. 第一轮参考执行属于环境校准；第二轮开发改进属于外部辅助优化；第三、四轮的设计判断归 BF。人工批准、具体工程指导和直接代写分别记录。

## 3. “每一步确认”如何执行

**一步指一个有明确出口的工作包，不是每条读取命令，也不是一整轮的无限修改授权。**例如，“核对接口现状”“验证一次器件放置与保存重载”“修复交付绑定”“测试一次受控恢复”各是一个工作包。

每个工作包遵循：

> 提交报告与拟执行范围 → 用户确认 → 只执行获批内容 → 原动作与受影响路径复验 → 提交结果报告。

同一批准范围内，不为每条正常命令再次询问。发现新问题、需要新的安装/发布/设计变更或需要扩大测试范围时，先记录，另报确认，不能顺带实施。安全停止和保留在途操作可以立即进行，不能以停止抹掉已发生的执行。

### 每份报告的首页

| 字段 | 内容 |
|---|---|
| 本次要证明什么 | 一项具体能力或候选判断 |
| 当前事实 | 版本、输入、实际回执和未检查部分 |
| 拟执行动作 | 修改/安装/调用什么，明确允许文件和工程范围 |
| 验证与结束条件 | 必须完成的真实路径检查；哪些结论可以是 FAIL 或不可评价 |
| 对已有结果的影响 | 哪些可复用，哪些变成 RECHECK_REQUIRED |
| 恢复与停止条件 | 保存点、异常/未知写入处理、何时停止原策略 |
| 需要用户确认的事项 | 精确到这一个工作包，列出不包含的后续工作 |

证据和日志放在附录。每份报告记录 Pi/Codex/人工职责、实际模型与环境配置以及费用口径。涉及方法实验时，实施前再声明假设、可推翻条件、对照、评价版本和主张边界。

**确认这份总计划，默认只授权下一步 R1-A 只读摸底。**它不自动授权写入探测、配置修复、付费 Pi 续跑或后面三轮。报告资料包沿用已有项目目录；执行事实仍以现有作业、候选与不可变回执为准。

## 4. 第一轮：基础环境与跨工具链路

### R1-A：只读摸底，先画整条路径

确认后检查实际版本、连接、权限、当前输入输出、既有成功证据及其仍有效的范围。读取精确作业和最新回执，不加载全部历史 Trace，不运行新的模型/求解或写入原生工程。

产出 `01_ENVIRONMENT_BASELINE.md`、`01_BLOCKERS.csv` 和实际证据索引。报告还要给出 R1-B 的有限探测方案：输入、工程身份、操作、副作用、回读和停止条件。

| 必经段 | 核对的真实交接 | 闭合证据 |
|---|---|---|
| 任务与恢复 | 原 owner、当前候选、未决操作、有效作业 | 重启后取得同一事实，不另建任务/重复派发 |
| 资料与约束 | 原始资料→可读内容→有来源的参数 | 文件/页段定位，事实与假设可区分 |
| 原理图修改 | 精确器件身份→放置/替换→引脚/网络 | 原生对象、网络、保存重载后的读回 |
| 原理图到 PCB | 器件/封装/网络→PCB 同步 | 实际 PCB、板框、连接与 DRC 结果 |
| PCB 到机械 | 实际板框/安装/接口→结构参数 | CAD 可打开，尺寸与装配检查绑定当前输入 |
| 电路到模型 | 当前连接/器件参数→模型输入 | 对应关系、适用域、真正消费的输入摘要 |
| 板级到固件 | 引脚/接口→官方 SDK/S132 目标工程 | 对应源码、ELF/HEX/MAP、构建与行为检查 |
| 固件到负载 | 实际策略/时序→运行负载 | 负载参数来源、阶段和任务事件对应 |
| 电源到任务/接收 | 源/储能/负载→事件→PC 解码 | 同版输入、波形/事件、接收与独立结果 |
| 检查到交付/恢复 | 候选/作业→报告/原生文件/包 | 自动绑定、可打开、重放说明、恢复原作业 |

统一标记：已有有效证据、已实测、待探测、被上游阻塞、不适用。不要把没有执行的环节当作无缺陷。

### R1-B：获批后做有限的真实探测

采用预先列出的参考操作，验证工具实际使用路径。至少需要一次真实写入—保存—重载—读回验证，以及下游输入、执行、检查、导出的衔接。

优先使用现有独立校准工程，不覆盖 P01。若需新测试副本或必须动原工程，应在 R1-B 报告中明确对象与影响，确认后执行。参考测试与 Pi 设计产物分开归档，不记为自主设计完成。

已有精确输入且资格仍有效的成功结果直接读取；未覆盖的行为用有限新测试验证。上游阻塞时，可使用标明来源的旧有效产物检查独立下游，但只算分段校准，之后仍需验证真实交接。

产出 `01_ENVIRONMENT_PROBES.md`，更新卡点清单，附拟修复工作包。此时可以出现设计失败；重点是工具是否完成动作、失败是否可信且可恢复。

### R1-C：报告获批后修关键阻塞，回放原失败

每批只关闭少数必经阻塞。优先顺序：写入结果未知/身份错绑 → 必经动作无法执行 → 数据跨工具不对应 → 结果无法检查或交付。先修复原失败消费路径，再用受影响的必要反例验证；不以内部函数单测或连接健康替代。

卡点最少字段：编号、触发动作、前置输入/候选、预期与实际反馈、是否产生副作用、影响下游、初步归因及确认程度、责任、修复范围、关闭证据、状态。

归因沿用：Agent 判断错误、工具执行错误、模型不适用、资料不足、任务约束不可实现、检查器错误。可以多因并存；“不可实现”不能由几次失败直接推断。

**第一轮出口：**必经环节均有覆盖记录；关键操作可执行且可读回；至少一条参考路径到达独立检查和导出；原失败有复验。核心模型缺失等证据问题明确保留，不能用占位结果宣称有效整链。其他任务能力和非关键易用性问题不阻止转入第二轮。

报告 `01_ENVIRONMENT_CLOSEOUT.md` 由用户确认后才进入第二轮。

## 5. 第二轮：严重使用摩擦与成熟能力复用

### R2-A：提交低效审查与有限基线方案

先分析已有公开轨迹、实际请求、工具回执和费用。当前 196 次请求未产生新写入/构建，是待解释的基线事实，不直接归因于模型、Skill 或上下文。

重点只选最严重的三类：重复帮助/参数探索；当前事实与压缩资料难以使用；恢复、等待和同版绑定导致返工。分别区分必要调查与重复无新增信息。

产出 `02_AGENT_FRICTION_AUDIT.md`，列出前几项浪费及修复层次。若现有轨迹不能支持比较，再提出一段小规模 Pi 基线供确认，不先恢复无限开放运行。

| 问题 | 优先落点 |
|---|---|
| 专业方法不清楚 | 复用当前兼容 Skill 的正文/参考/脚本 |
| 合法调用仍失败 | 接口实现/配置；回到第一轮缺陷清单 |
| 命令、身份和返回结构难用 | 工具合同、发现机制、结构化结果 |
| 手工对账版本、文件与哈希 | 确定性执行程序 |
| 恢复丢状态、历史挤占当前事实 | 持久状态及上下文选择 |
| 真正缺一项外部能力 | 先核对成熟 Skill/MCP/CLI 的兼容性，报告后接入 |
| 工具完成但设计错误 | 第三/四轮工程判断，不伪装成安装问题 |

不为了“采用 MCP”替换已可靠的 CLI；不全面重写所有 Skills；不再次把整个专业手册放入每次请求。

### R2-B：获批后改少量配置/方法，做可比验证

保留基础模型、thinking、任务与评价规则。确认实际加载版本；比较同类阶段的有效动作、重复读取/帮助、错误调用、恢复返工、模型和工具成本、专家提示量。并列原本地费用与必要估算，不替换账本，不将估算当供应商结算。

真实比较要明确输入和历史差异；仅“后一次看过更多答案”不算方法收益。单次请求字节减少不算效率通过。开发比较不是正式跨论文泛化或 RSI 证据。

### R2-C：结束报告

产出 `02_AGENT_METHOD_CLOSEOUT.md`，给出实际改善、未改善及剩余问题。

**第二轮出口：**Pi 可取得可靠当前事实，完成约定代表动作，不持续重复相同无效策略；恢复能继续原作业；剩余摩擦不阻止候选交付。费用不必最低，所有技能不必全面整理。

用户确认后进入第三轮；无法达到出口的阻塞有具体下一工作包，不自动再开全面架构重构。

## 6. 第三轮：由 BF 形成完整初版审查交付

### R3-A：BF 提出候选报告，用户确认

沿原 Pi 会话提出关键器件、接口、模型、固件/负载策略、机械约束与预期执行，形成 `03_CANDIDATE_PLAN.md`。BF 拥有设计判断；Codex 不预选最终电路或程序答案。

报告说明对当前候选的修改、复用的精确作业、需重验项、执行顺序和交付范围。用户批准这一个候选工作包后，允许范围内的设计、执行和检查不用逐命令询问；超出范围、改环境或改要求时另报。

### R3-B：获批候选实际执行

完成实际原理图/PCB/机械/模型/真实目标固件和接收程序；保存重载，执行独立检查，自动绑定同版文件。平台异常保存输入与副作用后另报；设计失败保留用于交付，不临时提高或降低验收门槛。

明确核对“失败候选审查包导出”和“采用为合格产品”是否分开。若缺少前者，作为第一轮遗漏的确定性接口缺陷，提交修改方案确认后处理，不能绕开产品验收或直接把 PASS 改出来。

### R3-C：交付与用户审阅

交付 `03_P01_INITIAL_REVIEW.zip`：一页概览；可编辑原生设计与程序；实际执行输入/场景；关键结果与独立检查；重放/依赖说明；来源/版本/介入记录；下一版的关键问题。

结果分别报告：

- **流程闭合**：必要原生动作和执行环节实际发生，检查实际消费同版输入，交付可打开。
- **数字产品**：PASS、FAIL、不可评价或尚未检查，按对应范围解释。
- **交付完整性**：文件、作业、源码与报告同版，或明确部分缺失。
- **自主性、物理验证、方法收益**：各自记录，不与前述状态合成分数。

允许交付“完整可评价但未达标”的候选；若关键原生操作、目标构建或有效整链输入缺失，只能交付部分审查包，不能称完整链路成立。

再提出一个小变更的验证工作包，经确认后从交付版形成子候选、重建受影响部分并比较，证明平台可以继续迭代。不要重跑未变输入的旧成功计算。

**第三轮出口：**完整候选与同版审查包形成，结果可以失败；用户能打开、理解和接手，并看到一次实际修订。文件存在、构建成功或 ZIP 完整均不单独授予整机通过。

## 7. 第四轮：按决定性缺口改进产品

每次只提出一个主要改进目标，报告后确认实施：先让基本任务成立，再扩展启动/输入变化/异常恢复等条件，最后改善尺寸、功耗、布局、制造装配和使用质量。

每个工作包包含：预计改善什么；哪些原有能力保持；候选差异；受影响检查；复用结果；采用/拒绝依据。保留已交付版，失败新候选不覆盖它。

产出 `04_PRODUCT_REVISION_XXX.md` 与对应同版工程包。若做 Agent 方法/RSI 研究，另交实验方案确认，固定环境和评价，不混入设备调试；未经新任务评价不宣称迁移或递归改进。

其他九篇只有在 P01 主链收口、迁移方案另报并确认后才恢复，仍沿原 owner。

## 8. 如何防止重新陷入零散递归修复

- 快速来自有限覆盖与复用证据，不来自省略保存读回、目标构建或独立检查。
- 先完成全链路卡点地图，不在首个故障处无期限探索；分段测试不能冒充已完成整链。
- 修复必须回到原输入、原动作和实际消费入口，而非新增一个更容易通过的演示。
- 相同输入、相同错误、没有新事实/假设/候选变化时结束原策略，登记清单；不自动通过改名字、改 owner 或重启会话重试。
- 在途未知写入先对账；本轮停止不撤销历史事实，也不清费用。
- 检查器纠错须有独立版本和受影响结论，不更改本轮产品目标。
- 每轮都有可看的实际产物，但只按本轮已经证明的范围报告。
