# SESSION_WALL_LIMIT 修复 — 2026-09-23

运行服务已更新。新交互消息的执行窗口为 1,800 秒（30 分钟）；Pi 进程与模型代理遵守同一个用户消息截止时间。累计美元、token 和模型请求次数限制保持原状。

## 这次故障

会话 `pi-chat-cf37636f82c771a4` 的进程运行了 600.0428 秒后，被 `launcher.py` 中的 `proc.wait(timeout=600)` 超时分支以 SIGKILL 结束，退出码 -9，记录为 `SESSION_WALL_LIMIT`。

同一轮的两次原生工程作业 `eng-12e30e7ccf3e4be7`、`eng-5242c9bb1f9a5ac0` 均已结束。第二次作业结束后约 16 秒，Pi 还在执行 `sleep 120` 等待命令，尚未读回结果，就到达了启动器的固定进程寿命。这些作业结束不代表产品检查或交付通过。

原设计同时有“每条用户消息 600 秒授权”和“Pi 进程从启动起最多 600 秒”两套计时。即使使用者在运行中追加了消息，模型授权更新了，进程计时仍然不变。此外，产品建模自身允许最多 900 秒，与 600 秒进程限制不相容。

## 修改

1. 新交互消息统一使用 1,800 秒授权。模型派发、实验授权和 Pi 进程监督读取同一个持久化截止时间。旧消息的授权不追溯延长。
2. 交互启动器跟随最新有效用户消息，而非固定进程年龄。新增消息可取得新窗口；重复 operation、后台重试、模型自续跑不产生新授权；撤回后的授权不再有效。
3. 到期先发送 `close`，给 Pi 10 秒结束当前工具、保存状态并退出。只有不响应关闭的进程才被强制清理。会话和回执记录 `PAUSED`、截止消息、观察时刻及是否强制清理，不能记成产品完成。
4. 最终暂停状态在日志线程读完退出事件后才写入，修复退出时的迟到事件将暂停覆盖成失败的竞争条件。到期决策与新消息写入串行协调。清理期间新增的消息留在队列，旧进程退出后按新消息授权启动，避免把新输入交给即将关闭的进程。
5. 任务页显示“已暂停”及中文恢复提示，原 `SESSION_WALL_LIMIT` 也有中文说明；旧超时保留为真实历史，仅在后续确有模型回复时折叠为历史中断。
6. 科学批量运行仍为固定 600 秒。原模型 USD、token 和次数边界不变；没有删除旧失败、清空账本、自动重发原产品任务或产生付费测试。
