## 4. 审计恢复与重复读取已修复

`audit_checkpoint.py` 为每个检查记录输入设备/文件身份、大小、纳秒修改/状态时间、检查代码身份与上下文。输入或规则变化会失效；检查中修改输入也会拒绝。对同一 inode 的硬链接只进行一次完整读取，但各清单引用分别校验哈希、字节数和读回标志，错误引用不能借用另一个引用的成功。

压缩文件在一次顺序读取中同时得到压缩文件哈希、解压后哈希与字节数。每个档案/末端电流检查完成后原子保存检查点。整个运行审计还绑定外部器件模型、编译器和 NumPy 版本；最后报告写出失败时可重新汇总已完成结果。报告目录和 NumPy 标量序列化在大读取之前先做小样本检查。并发解压限制为一个，避免与下一项求解争抢资源。

16 MiB 随机 gzip 夹具实测：首次读取 0.0350 秒，硬链接续查 0.000208 秒，两次只发生一次档案读取。它证明检查点命中与去重有效，**不是 1 GB 原生任务或整机端到端提速测量**。

## 5. 本轮没有启用的效率改动

D5 求解器内部的同步 RAW 归档仍保持原样。把它移出迭代等待链还需要新的执行器版本：先保存供后续迭代使用的轻量结果和恢复点，再交给单工作者、有限待处理容量的归档队列；只有归档读回通过才删除 RAW，发布封存再等待归档完成。队列还必须处理失败重启、磁盘背压及任务结束时的排空。

这项不能仅修改函数后便宣称旧 D5 的执行器身份仍相同。本轮按要求不重启已经通过的整机仿真，也没有放宽 `reference_ready` 的哈希门槛。因此它单独列为后续执行器版本的工作，**不计作已完成**。当前改进已经覆盖本地路径、审计恢复、对象去重、范围化验证和存储清理。
