# Executable knowledge — software delivered, promotion rejected

The guided reference study executes 49 experiments per materialization: four
source interventions, six held-out explanation conditions, and 39 experiments
across the three future-task search drivers. Every experiment is content-addressed
and reproducible. These counts exclude earlier development retries and do not
claim full wall-clock or monetary cost accounting. External model calls: zero.

## What actually happened

- Initial 330 µF / 18 Ω design lost power during TX.
- Removing ESR alone still failed. Reducing TX demand or increasing storage
  restored execution. This does not uniquely isolate every transient mechanism.
- Completed action-load records parameterized a developer-authored burst model.
- Its program runs from a copied directory using isolated Python and no original
  conversation or reference-engine imports.
- Six fixed explanation conditions gave a maximum error of about 4.99 mV against
  the independent reference implementation (80 mV gate). Both implementations
  remain in the same simplified model family; there is no hardware evidence.
- On the first three new tasks, raw search needed 5, 7 and 6 experiments;
  a classical text-energy inequality needed 2, 3 and 2; the capsule needed one each.
- The fourth task had no passing design in the fixed candidate list. Raw search
  used eight experiments, the energy rule three, and the capsule admitted none.
  Zero experiments here does not mean successful design or a proven impossibility.

## Failed gate is a result, not a bug to conceal

The prespecified whole-use gate required all four tasks to succeed. It failed.
The task, design list and gate were not adjusted after seeing the result. The
capsule is retained in a **REJECTED** qualification state, even though three tasks
show useful transfer. There are **zero promoted research knowledge objects**.
The optimistic mean-energy-only candidate is also retained as a negative control.

The build command returns a completed experiment record with
`status: qualification-failed`; it does not promote the candidate or report a
scientific pass. Software tests explicitly require the fourth task and rejection
to remain visible. This is how a functioning scientific apparatus records a
negative result while its implementation tests can still pass.

## Scope and architecture

`knowledge/burst_program.py` is a standalone, standard-library-only program.
Its action-load parameters come from traces; program structure is developer
authored, not autonomously discovered. Scope is a precharged no-harvest burst,
fixed action program, specified capacitance/ESR/voltage/TX ranges. It does not
predict diagnostic correctness, radio delivery or complete VMS.

`knowledge/registry.py` hashes the program, parameters, provenance and version.
Lifecycle decisions are hash-linked and reject participant self-promotion at the
API level. This role parameter is not a security boundary on an unrestricted
developer filesystem; a formal qualifier must be a separate trusted service.

The GUI shows four linked views: failure/interventions, source program and scope,
explanation/use receipts, and future-task removal/transplant comparisons. It
renders recorded outcomes and does not recompute scientific verdicts.

## What this does not establish

The three drivers are deterministic controls, not equal-history LLM arms. No
autonomous Agent study, recurring capability growth, general Harness improvement,
learned policy factorial, cross-device result, measured hardware, or RSI claim.
Further research must preregister a new study; do not relabel the failed gate.
