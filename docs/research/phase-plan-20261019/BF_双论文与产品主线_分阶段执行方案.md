# BF 双论文与产品主线：分阶段执行方案

日期：2026-10-19  
状态：已确认，按阶段执行  
组织：一个主管会话 S0，两个执行会话 A、B，沿用现有会话身份。

> 总目标：围绕无电池（Battery-Free，BF）系统的设计与自我改进，用一套共享实验底座推进 A/R 产品线和两篇论文。研究贯穿采能、储能、启动、程序活动与有效接收；每个阶段交付可运行成果、实际实验数据和对应论文内容。

## 一、最终要交付什么

| 交付方向 | 最终成果 | 完成标准 |
| --- | --- | --- |

**A/R 是同一条产品线。** A 是光供能基础节点，R 是它在周转箱上的状态、历史与恢复服务。现有压电节点和 P01 继续用于参考、回归和已有经历分析。

### 两篇论文的核心问题

- **论文一：设计无电池系统时，要判断能否完成规定服务、决定怎样修改采能、储能、电源与程序，需要保留哪些能量、时序、状态和信息有效性？Agent 怎样发现并补足遗漏的接口信息？**
- **论文二：无电池设计 Agent 怎样从启动、掉电、供电—负载反馈和服务失败中改进设计方法？怎样可靠评价这些改进、迁移到新 BF 任务，并提高改进器产生有效后代的能力？**

论文一暂定题目：**《面向无电池系统设计的接口充分性与反例驱动信息精化》**。研究对象是 BF 系统中足以支持服务判断和下一项设计选择的信息边界。

论文二暂定题目：**《面向无电池系统设计的耦合范围评价与可迁移自我改进》**。研究对象是 BF 设计方法怎样从经历中改善，以及怎样用可靠、经济的验证积累这些改进。

### BF 特点怎样进入方法与实验

| BF 机制 | 需要调查的接口信息 | 支持的设计判断与实验 |
| --- | --- | --- |
| 能量间歇到达与积累 | 源波形和能量到达顺序、初始储能、漏电、容量及源对负载的响应 | 是否能在服务窗口内积能与执行；比较总能量相同、到达顺序不同的情况 |
| 冷启动、欠压与复位 | 启停门限、迟滞、启动能量与时长、供电有效信号、复位条件 | 何时真正可启动、能否完成一次任务；比较平均预算相同、启动行为不同的情况 |
| 电源与程序双向反馈 | 供电状态、程序事件、持续时间与电流来源、负载导致的电压变化 | 改程序后供电怎样变化、供电又怎样改变执行；决定联合求解和重新验证的范围 |
| 掉电后的状态与信息保持 | 易失/持久状态、写入能量与原子性、复位后的时钟和恢复行为 | 历史和事件是否保留、是否重复或错时；比较服务跨掉电前后的连续性 |
| 感知与接收的有效窗口 | 事件有效期、采样时刻、发送与接收完成、截止时间及新鲜度 | 收到的是否是所需时刻的有效信息；比较能量满足但采样或接收过期的情况 |
| 换能与安装边界 | 结构与夹持、光照或振动条件、换能器身份、负载相关的源模型 | 改结构、器件或安装后，原供能结论是否仍适用；确定需要补充的模型或物理核对 |

每项 BF 任务按服务目标、工况和允许修改的变量选择所需信息。已验证包络内的局部修改可以保持简洁接口；启动、掉电、事件保持或反馈改变时，再调查并补充相应信息。信息包记录数值、单位、条件、来源、生成者、实际消费者和失效依赖。

### 两篇怎样分工并连接

| 研究层 | 论文一 | 论文二 |
| --- | --- | --- |
| 一次 BF 设计 | 找出决定服务成败和设计取舍的缺失信息，验证补充后的接口 | 利用这些信息选择观察、联合推理、实验和重执行范围 |

### 共用底座与并行规则

1. **共同版本。** S0 从当前集成成果及已验证的存储修改形成下一版源码清单。根仓库和 V2 的 Git 历史分别登记，所有执行工作区从相同内容基线恢复。
2. **独立写入。** 每个会话一个活动工作包，明确 `owned_paths`。公共源码、任务合同、检查器和共享状态由 S0 单写；A、B 各写自己的模块、测试、数据和稿件。
3. **模型并发。** 同时最多三个活跃模型执行体，Codex、Pi 和临时工作者一起计数。进入真实 Pi 试验时，由 S0 排程释放槽位；先保证串行正确，再验证并行收益。
4. **共享资产。** SDK、固定模型和有效结果只读共享；候选、数据库、临时输出和账本隔离。原生 EDA、许可证和硬件使用全局资源锁。
5. **结果复用。** 执行输入未变且仍有效的成功计算直接复用；要求或检查规则改变时，优先对原始结果重新评价。反馈环受影响时，将重算范围扩到完整反馈环。
6. **存储。** 每批先登记峰值、输出目录和保留上限，满足“10 GB 余量＋预计新增峰值”后派发。保留一份规范原始数据，阶段结束整理可重建临时文件。
7. **同步。** 在基线发布、接口变化、工作包交付和阶段验收时同步；交接文件包含输入版本、代码差异、实际结果、复现命令和下一依赖。
8. **研究身份。** 固定 BF 服务目标、供能工况、初态、允许的外部能量/人工动作与正式判据；接口、分解、上下文和方法作为研究变量。开发集、选择集和最终测试集分别登记，两篇共享暴露记录。

### 共用开发要求

- 工具 schema、模型实际看到的说明、示例和校验规则使用同一份定义。
- 修改后的完整源树进入实际构建和求解，随后绑定候选、验收记录与交付包。
- 新检查结果追加保存；检查器和科学语义变化各自升级版本，并核对受影响的历史判断。
- 验证顺序为定向测试、实际消费路径、适用的 `./init.sh` profile、结果读回、差异审查和临时文件整理。
- 原生写入先确认当前工程身份，完成后保存和读回；未知状态先对账，再决定恢复动作。
- 每个完成工作包都有复现命令、结果与下一交接；共享状态由 S0 统一更新。

### 两条方法链要实际发生什么

**论文一方法链：**

BF 任务与当前候选 → 在合法修改空间内发现相反服务结果或判断冲突 → 定位可能遗漏的能量/时序/状态关系 → Agent 提出资料查询、观察或实验 → 执行并独立核对 → 更新接口 → 对同一 BF 服务和下一项设计修改重新判断。

既有“研究者给公式、程序负责生成文件”的入口继续作为构造基线。新方法要记录 Agent 怎样提出信息，以及它付出了多少取得与验证成本。

观察发现试验固定可访问的器件资料、程序、BF 模型、测量/计算工具和合法实验空间；目标观察与相关字段标签保留给独立评价。目录内选择与目录外构造分别计分。生成的观察需要进入实际消费者：例如复位后的采样状态进入事件保持检查，电压驱动的负载行为进入联合执行。

**论文二方法链：**

BF 启动/掉电/服务失败经历 → 改进器提出 H′，调整信息获取、设计顺序、共同上下文或实验策略 → 按 BF 耦合确定受影响范围 → 筛选 → H′ 重新完成设计 → 独立确认采样、信息保持与有效接收 → 保留或拒绝 → 记录适用的 BF 工况和任务。

全局提示变化从 BF 任务入口开始。局部状态复用核对储能、供电、程序与持久状态，以及边界对新行为的响应；负载改变供电、供电再改变程序时，将验证范围扩到完整反馈环。按任务要求评价掉电后的正确恢复、历史保持与接收时效。

### 迁移怎样区分

- **需求迁移：** A/R 光供能测温服务迁移到 O 的无电池办公设备开始/持续/停止事件服务，重新核对事件保持和时效要求。
- **机制迁移：** 改变能量到达模式、启动/复位、信息保持或反馈关系，测试方法能否发现新的必要信息。
- **设备迁移：** 在另一个已资格化的 BF 器件或采能案例上运行，例如从光供能条件扩展到具备资格的振动/压电条件。
- **改进迁移：** 由 BF 开发经历形成的 H 规则，在未用于选择它的 BF 任务上重新完成设计。
- **递归改进：** 比较 G0 与 G1 在相同 BF 起点和预算下产生的方法后代质量。

P-D 与 C-lite 按案例目录的既定含义，在有明确 BF 研究问题时接入；物理机制与系统抽象分别归档。已用过的 P01、压电和 B 开发任务继续标记为已见。迁移矩阵逐项登记服务要求、采能源、器件、状态保持机制和合法变量发生了什么变化。
