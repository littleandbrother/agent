# M3：从电压阶段推进到记录交付的服务修复

派发：`BF-PQE-SERVICE-REPAIR-M3-20261023-001`。接续 M2 独立收口；S0 统一安排 A/B，不重开 M2，不等待下一次定时审查才开始本包。全仿真，原服务、模型、设备观察能力和合法动作不变。

## 为什么现在改方向

M2 的题1中，冻结反馈与完整反馈选择同一候选，均 PASS6。题2中，两者三次行动完全相同，接收数 3→5→5，完整反馈多做了评分而未改善服务。当前 `failed_phases` 主要描述 BOOT/SAVE/TX/ACK 内欠压；它不能充分表示“记录已保存、发送完成，却没有在期限内交付”。第二候选存在保存记录跨冷周期迟到、末尾队列未清空。接收序号本身没有重复，不能把终评的综合错误标签直接解释成序号生成故障。

因此本包研究的是：**在能量与信息共同决定服务的 BF 系统中，逐记录的失败证据能否改变 Generate/Select/Update 的实际行动，修复迟到交付，同时保持原启动、事件保存和期限要求？** 不继续围绕同一个电容方向重复扫描。

可反驳假设：新增服务状态确实引起不同的合法干预，并改善当前任务的及时有效接收或取得可验证的失败边界。状态已进入 Update 却不改变候选/选择，或改变行动却没有上述后果，都反驳本包对应的收益主张。S0 在新 feature 开始前一次写明各 owner 的源码/产物路径、协议变化和直接验证入口，沿用现有所有权规则。

M2 的通用组另受本地请求体上限阻断。三次真实请求均结算，第四次在转发前 BODY_CAP 拒绝，不能计为通用方法的科学失败。原占位、原始错误与三次费用保留；M2 的三条件比较不完整。本包使用新公共投影与新方法版本，所得结果不得回填 M2。

## A：把失败解释落实为可计算的服务关系

1. 用 M2 题2的既有公开 records、packets、receiver_records、活动与程序状态，连接 SAVE→重发→接收→ACK→队列移除。区分同记录重传、不同记录复用序号、迟到接收与未收到；没有可观测依据的身份关系保持 UNKNOWN。私有真值和终评只供独立核对，不流入方法。
2. 明确候选需要预测的关系：记录年龄/剩余期限、供能结束后的可用能量、网关恢复后的发送机会、重试消耗、掉电保持和队头阻塞。保留竞争解释，不能从一个迟到标签推导全域无解。
3. 提供共享事实提取与有适用域的便宜预测。可以延伸现有近似，但不能把完整动态求解隐藏成便宜调用；完整消费者的调用全部计入动态预算。模型不能覆盖的重试/复位/队列后果显式为 UNKNOWN。
4. 至多两次有事前预测的工程候选执行，使用原合法动作检验关键关系。优先研究已有 `retry_s` 与发送门限、储能的联合关系；不预设增大重试间隔必定有效。设备仍无新增绝对时钟或未来网关状态观察能力，不把仿真已知环境直接变成固件可观察信号。

交付是一个实际服务关系、最多两个工程后果及其适用边界。工程参考的具体成功配置不注入参与者；共享公式、模型与资料对两组同等开放。若原动作空间不能表达所需修复，指出具体能力缺口；不能改变服务或偷偷扩动作后宣称原任务已解决。

## B：让关系真正进入 G/S/U

- **Update**：把有证据的交付失败写成当前可消费的记录/队列状态与竞争解释，区分支持、反驳、不可区分和未完成执行；不再用 `failed_phases=[]` 表示没有值得响应的问题。
- **Generate**：在原许可域产生程序重试、发送门限与储能之间有理由的候选，也允许取得能区分原因的观察；不能只重新列出原来的源端增强方案。所有候选记录预期后果和可能伤害的约束。
- **Select**：在候选的适用域内比较及时交付机会及能量/启动代价；预测不了的部分不得靠统一 −1 同分后仅按改动数决定其工程优劣。必要时选择一项有判别力的执行，而不是伪造精确排名。

先用保存轨迹检查新状态是否确实改变候选或选择；这只是软件行为证据。随后必须进入原动态消费者，由独立结果确认。新逻辑是开发者实现的工程方法，不称自动 H 学习。M2 版本和结果保持冻结。

## S0：公共调用减负与实际闭环一起完成

公共调用只发送当前任务/设计、必要事实摘要和结果索引；较长波形、逐事件细节、源材料和历史预测通过同等可用的分页/按需工具读取。历史结果不重复嵌入每轮上下文，原始完整公共事实继续可取得。摘要不得夹带推荐动作或私有诊断。新投影对两组统一，不削弱通用组的信息权限。

本轮已定位的两个直接来源是 `public_tool_results` 累积完整预测列表，以及公开材料在当前 evidence 与历史 visible_before 中重复。应保留每份预测原有标量、失败/未知/适用条件及列表数量和读取入口，按稳定对象身份＋section＋offset分页；同时限制行数和字节数。不要把完整对象搬进同一次 prompt 的 registry，或用 top-k 筛选替参与者决定值得看的结果。

维持原 broker 请求上限。派发前对实际序列化负载检查大小，分页结果也有明确上限和后续入口。对明确的本地转发前拒绝记工具未执行；只有可信转发/供应商事实能决定请求与费用状态。不能仅因缺少 request id 就把可能已发出的请求当零费用；真实新 usage 缺失仍立即停止依赖调用。

只做一次受影响路径的离线检查：多轮公共工具结果不再无限膨胀、完整资料仍可按需读、明确预转发拒绝与已发送后 usage 缺失分开。无需付费格式探针。入口可用后直接完成下述两条有限轨迹，不把投影修复当成另一个等待审查的终点。

## 最小运行与结束条件

这是已见题2上的新版本工程开发，不是未见迁移。共同起点采用 M2 题2第一项已评价的失败候选及同一份公开历史；具体起点在执行前由 S0 一次固定。旧成功配置、A 私有参考与终评不能进入参与者。

运行两条轨迹：

1. 强通用 Agent，使用相同的公开记录关系、便宜预测、资料、合法动作与评价。
2. 新固定服务 G/S/U，实际执行 Update→Generate→Select→原消费者；无需再调用模型装饰确定性步骤。

每条至多三个不同已评价候选，精确缓存同样占候选名额。最终候选若出现改善，最多各一次在 M2 题1原条件复核是否伤害启动和完整服务；精确已执行输入直接复用。比较实际服务、首次可行成本、失效是否转移、行动差异、错误采用及全部形成/执行成本。新共享能力与新策略同时改变，不能单凭旧新对比声称 Update 的独立因果增益。

有限上限：

- 一个付费通用 episode：12 请求、24 工具、900 秒、总输出 65536 token、每请求最多 32768 且不超过剩余额度、USD 5。一个确定性 G/S/U 轨迹，900 秒。
- 最多 10 个新完整动态输入：A 工程验证2 + 两轨迹候选6 + 条件回归2。每次120秒、总1200秒；缓存复用单列，不重跑已有成功。
- 最多60次近似评分：A最多12，两轨迹各最多24。native、H/G形成、物理执行均0。
- 新增产物最多80 MB、峰值0.8 GB；新批次一次确认10 GB余量加峰值，复用原环境/源树，不复制周期或新建备份。
- 最多两次有理由的实现修订，参与者结果前冻结公共工具和方法。结果后不调参救组、不补跑、不转移未用额度。若遇具体工具阻断，保留未执行格；不把它计为方法失败。

成功出口是记录交付链得到实际修复，或形成明确条件结论/有证据的失败边界。只给 FAIL 标签、逐点失败或未执行，均不能说明全域不可行。若新方法仍选择同样行动，必须指明哪项新增状态未进入生成/选择；若行动改变但无收益，保留预测失效或动作不足的具体证据。两条轨迹后收口，不自动开展第三轮同轴矩阵。
