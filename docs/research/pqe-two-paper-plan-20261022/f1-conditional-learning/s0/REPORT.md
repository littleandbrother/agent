## 实际方法、行动和服务

- H2 以一次 G-PROPOSE 返回空补丁。H4 实际执行 G-ATTRIBUTE 比较方法缺陷、消费者差距、任务欠规定、工程不可行和未决解释，再以 G-PROPOSE 返回空补丁。两次均正常结束、用量已知，无拒绝、截断或无效补丁可修。没有新代码、提示或条件被装入为自动后代，四个后代格按事前规则跳过。不能用父方法的结果替代后代证据。
- 所有六个执行格都真正消费共同初态 FAIL 的 Update 后才进入 Generate；H0 没有额外开发历史，H1/H3 使用相同冻结历史，形成阶段未获得新任务或初态。各求解格不共享别格结果。
- t1 的 H0 先观察初态，然后实际修改机构/储能/门限；第二、第三候选虽然均收到6条记录，却分别触发 `assembly_envelope_exceeded` 和 `cam_pressure_angle_exceeded`，原判据为模型域 UNKNOWN，不算通过。
- t1 的 H1 将电容改为约433.31µF、ESR0.1Ω、启动1.9V、TX门限约2.0369V，机构改为基圆约6.8677mm/行程8.5mm。原完整消费者得到 SAVE/TX/RX/ACK 各6，6个及时匹配，模型有效；最低发送端电压约2.2284V。
- t2 的 H0 仅把 `persistent_queue` 从 false 改为 true，原完整消费者得到 SAVE/TX/RX/ACK 各6、及时匹配6。H1 先观察初态，再独立提交相同编辑；输入完全相同后才复用已经保存的完整结果。H0 已能解决这一条件，不能把这一修复归因于自动学习。
- H3 的人工代码确实在初态 Update 和后续位点加载、触发，但两题实际各选择两次相同 observe，没有提交修复编辑。后续 Update 在隔离接口停止，不能据此称人工规则的工程修复劣于父方法。

## H3 错误定位与采用

`hook-error-readback.json` 以各格最后一次原 invocation 的 context SHA 精确匹配，只读重建原始输入帧：t1为2,461,796B，t2为2,124,991B，均超过未变 restricted_worker 的2,000,000B上限。原 Harness 保存了 HOOK_ERROR 状态但丢弃了异常文本；上下文哈希和原 `_encoded` 的确定性检查定位到写入worker前的帧拒绝。没有重跑hook、模型或仿真，也没有扩大上限或救援格。

H1 两题均 PASS，但 H2/H4 没有合格后代，外部范围、服务、成本采用比较均无后代可进入；保持同历史父方法。形成费用仍完整计入，不挪用未执行格额度。主瓶颈是形成选择了合法 no-update，没有发生“修改H→改变行动→改善服务”的自动链；H3 另外暴露了重复观察和累积历史的隔离输入容量边界。
