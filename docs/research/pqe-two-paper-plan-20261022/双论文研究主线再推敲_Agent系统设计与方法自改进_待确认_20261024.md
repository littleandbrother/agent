## 1. 先纠正上一版：容易验证，不等于抓住了核心问题

上一版两项建议存在实质性收缩：

- 第一篇先由我们写出启动、储能与服务之间的关系，再让算法传播约束、联合搜索。人的关键设计判断已经提前进入模型，Agent 接到的是整理好的求解题。
- 第二篇先由我们规定状态特征和可选动作，再学习何时选择哪项动作。即使选择更准确，也主要证明策略学习，尚未证明 Agent 学会改进自己的系统设计方法。

用户的质疑成立。这两项可以作为内部求解工具和对照，**不再单独承担两篇论文的主要创新主张**。

我们需要减少的是案例数量、产品完整度和外围工程，不应删掉研究问题最困难的部分：**谁来决定怎么描述问题、怎么拆分功能、哪些东西必须一起设计，以及经验如何改变下一次做这些决定的过程。**

但也不能反过来要求方法完全脱离优化、主动学习或程序合成。足够宽泛的编码可以把架构、程序乃至 Agent 自身都写成优化变量。真正要比较的是：在同样组件、事实、设计自由和资源下，我们提出的具体计算过程，是否提供了已有强方法没有显示的能力或效率。

## 2. 两篇论文应当共享哪条研究链

先区分三个对象：

| 对象 | 具体是什么 | 改变它意味着什么 |
|---|---|---|
| 产品设计 D | 组件连接、储能配置、事件保持方式、固件状态机和通信程序 | 做出另一个设备方案 |
| 设计方法 H | 如何解释服务要求、建立系统关系、分配组件功能、生成方案、选择实验和利用结果的程序 | 下一次面对问题时，Agent 的设计过程改变 |
| 改进方法 G | 如何从经历中提出、测试、修改和选择 H 的程序 | 产生有效设计方法的过程改变 |

**论文一的核心：固定 H，研究它能否自主修改系统的功能分配与组件交互，并落实到 D。**

**论文二的核心：从论文一这样的真实设计经历中修改 H，使它在新问题上更会构造设计过程。**

因此，两篇不是“优化设备参数”和“优化参数选择器”的平行应用。第二篇学习的对象应当包含第一篇中真正困难的设计步骤。如果这些步骤仍由开发者写死，第二篇就不能用一般性的“设计方法自改进”来命名。

G 自身再被改进属于更强的一层。它可以保留为研究目标，但标题若使用“递归自改进”，就必须另有固定起始 H、相同历史和预算下 G0/G1 产生后代的比较。不能用 H 的多个版本或一条上涨曲线代替。

## 4. 论文一：从服务失败反推功能分工，再联合生成结构和程序

### 4.1 唯一核心问题

> 当初始组件分工无法完成系统服务时，Agent 能否从执行后果中发现该改的是分工与交互，并自主产生新的功能分配、结构连接和控制程序？

例如，“检测事件”未必总由主处理器在启动后完成；“保留信息”未必等于写一个存储变量；“确认交付”也不应由发送成功标志替代。系统级设计涉及这些职责由谁承担、何时承担、跨越什么失效过程，以及各组件承诺的条件是否相容。

论文不必囊括所有机械、电源、通信、温度模型。**但至少一次实质性的跨组件功能重新分配，必须由 Agent 产生并进入可执行设计，不能由我们提前写成完整可选方案。**

### 4.2 一个说明问题层级的门体例子

以下是拟议机制例子，**不是已经观测或验证的项目结果，也不是要直接放进测试提示的答案**。

假设门动作同时提供短时能量和待记录事件，但事件结束早于主处理器启动。当前方案让处理器启动后才采集事件。

这时有三种层次不同的设计：

1. 调储能和启动门限，争取让处理器更早工作。这可能有效，不能预先排除。
2. 如果合法范围内仍不能覆盖事件，改变捕获事件的职责：让能够在该时段工作的组件先保留事件状态，主处理器稍后读取。
3. 第二步必须连带生成交互程序：什么时候读取、如何生成记录身份、何时提交、何时清除前级保持状态、丢 ACK 或再次复位时怎么办。

其中一个候选可能使用被动保持机制，但不能把它当免费答案：保持容量、机械代价、读取与清除能耗、重复事件和时间信息都要有实际模型。一位锁存器不足以保存多次事件及其时间，不能为了得到成功而削减原服务。

这个例子的要点是：**事件捕获的承担者和交接时序变了，系统因而具备原分工下没有的行为。**只增大电容，或只在日志里增加“事件已保持”的字段，都没有完成这一步。

如果现有仿真不能表达这样的功能重新分配，应在方案确认后增加最小、真实有代价的组成能力。不能因为已有工具只支持几个参数，就把整个研究目标改成参数调优。也不能只给所提方法新增能力；所有对照必须拥有相同组件和程序自由度。

### 4.3 具体计算对象：不是一张固定的失败类型表

Agent 维护一个可修改的工作问题表示 P：

```text
服务义务：需要产出什么信息、在哪个时间窗口、满足什么完整性
功能分配：哪个组件负责捕获、保持、计算、计时、发送和确认
交互关系：生产者、消费者、数据/能量、有效条件和交接时刻
当前实现：具体连接、参数、状态变量与程序
未解决关系：哪些假设得到支持，哪些被反例破坏，哪些仍未知
```

服务义务来自固定的用户要求；其余部分可以由 Agent 构造和修订。P 不是隐藏判定器，也不允许通过重写 P 放宽服务要求。

P 的条目必须能绑定到实际组件、程序变量和可公开读取的执行结果。“识别到跨域冲突”这样的文本不能直接当作有效状态。

### 4.4 拟研究的核心算法：按失效关系选择重设计范围，并重新分配职责

算法重点不在新增一个约束求解器，而在求解器之前和之后：**当前应重新设计哪一段系统关系，怎样把功能换一种方式交给组件，并形成能够整体执行的新方案。**

具体执行过程如下：

1. **从完整服务失败定位交接缺口。** 根据公开结果，沿“事件或采样产生—记录保持—交付”回溯，列出可能破坏服务的交接关系。记录竞争解释；轨迹本身不足以定因时，选择一次能区分解释的合法执行。
2. **构造重设计范围。** 先取受影响的功能、生产者和消费者；同时纳入它们依赖的供能与状态保持关系。范围是 Agent 的候选输出，而不是开发者按故障名称分配好的模板。
3. **重新生成组件责任。** 对该范围内尚未满足的功能，搜索哪些可用组件能够承担、需要怎样连接、会新增什么状态和程序步骤。允许原分工不变，也允许跨组件移动职责。
4. **联合合成候选实现。** 输出必须同时含结构/配置改动与可执行交互程序；必要时修改 Agent 自己用于预测的动作模型。不能先假设一个理想硬件行为，再让固件在其上虚构成功。
5. **用固定完整消费者执行。** 新程序的负载重新影响供电，新供电重新影响启动和执行；原服务逐项判定。产生新反例时，保留已实现部分，重新判断重设计范围是否漏了必要关系。

可写成：

```python
while budget_available():
    gap = locate_unfulfilled_service(current_design, public_results)
    region = propose_redesign_boundary(gap, current_problem, component_facts)
    assignments = synthesize_function_allocations(region, allowed_components)
    candidates = jointly_realize_structure_and_program(assignments, boundary_conditions)
    design = choose_executable_candidate_or_discriminating_test(candidates, evidence)
    result = full_simulation(design)
    current_problem = revise_from_actual_result(current_problem, design, result)
    if complete_service_pass(result):
        return design
return supported_result_or_unresolved_gap()
```

这些函数需要真实程序实现。重点观察 `propose_redesign_boundary` 和 `synthesize_function_allocations` 是否产生此前不存在的设计过程；仅用这段伪代码包装原先四套候选表不算完成方法。

初版可使用 LLM 提议关系和程序、传统求解器求局部参数、直接仿真判定。没有必要先做通用定理证明器或第二套高保真状态机。

为了避免上述函数又成为空壳，首版把中间输出具体化为以下对象：

```text
一项交接关系：
  信息/资源是什么；谁产生；谁消费；产生时间；最晚使用时间；
  在此期间由谁保持；该保持方式需要什么能量；何时失效。

一个反例：
  对应哪条服务；上述哪项关系与实际结果不符；
  是真实缺失，还是当前观察无法确定；原始结果引用。

一个联合改造：
  被移动/拆分/合并的功能；新的承担组件；新增状态及读写者；
  组件连接改动；程序改动；预期改变的交接关系；仍需检查的外部条件。
```

重设计范围的生成采用**从失败交接向外扩展的有界图搜索**，而不是“看到某标签就调用某方案”：

- 起始范围包含该交接的生产者、消费者和保存它的状态。
- 一个候选若改变状态写入位置，必须把该状态的读取与清除路径纳入共同修改，或给出它们仍然兼容的可检验条件。
- 若改变某个程序阶段的执行时刻或次数，必须把相关供电约束带到边界，重新执行供电—负载反馈；不默认原电压仍可用。
- 对每个范围，生成少量不同的功能承担方式，并把它们展开成结构与程序候选。
- 完整执行产生范围外的新失效时，依据那条实际依赖扩大范围，而不是无条件同时重写全部组件。

这里的新算法候选，具体就是**怎样利用服务交接反例，搜索需要共同改造的系统范围，再在其中共同生成分工和实现**。读取/清除依赖检查等基础正确性对所有方法公开；不把专属工具返回的正确改造范围喂给所提方法。

这个搜索并无已知的全局最优或完备保证。它的价值假设是：相比全系统无差别代码搜索，它减少无关组合；相比固定分解，它能扩大到真正需要改变的关系。两边都必须通过对照验证。

### 4.5 “真正超出已有方法”的候选步骤在哪里

候选差别是：**执行反例不仅修正一个给定系统的模型，还决定重新设计哪一段组件分工，并生成该分工的新实现；新实现又改变需要建模的交互。**

这比上一版“已经知道冲突方程，接下来求解”多了一项实质任务：形成那个值得求解的系统设计问题。

但不能据此声称所有已有方法都做不到：

- 与 WorldCoder、TheoryCoder-2、SkillWrapper 相比，主要变化是被建模的设备本身也由 Agent 重设计；它不仅学习给定技能怎样工作。**这首先是研究问题差别，还需要上述具体算法带来收益，才有方法贡献。**
- 与组件合成、RoboGrammar 相比，不能只说“我们也生成结构”。要验证由反例构造重设计范围与功能分配，比在共同原语上直接进行结构—程序搜索更有效。
- 与通用工程 Coding Agent 相比，不能靠更多工具或隐藏的专家方案取胜。它也应能自由改完整设计；我们只多一个可检验的计算机制。

**建议的主张是“反例驱动的功能分配重构算法”，不是“第一个会系统设计的 Agent”。这仍是研究假设，不是已取得的创新结论。**

### 4.6 核心实验：验证谁完成了问题构造

先做一个能够完整展示上述链条的机制实验，保住假设后再用少量不同机制实例验证；不先建设巨型基准。

**共同输入：**原服务、组件能力与代价、允许组合的原语、公开仿真接口和初始设计。不给任何一组完整修复方案或正确功能分配。全部组允许使用同样的新结构和程序能力。

**三项主要比较：**

1. 强通用设计 Agent，能自由建模、编程、调用完整仿真。
2. 相同原语上的直接联合结构/程序搜索，使用反例反馈和合理的传统求解工具；有改动的部分明确为适配实现。
3. 所提方法。再做一次关键消融：冻结其功能分配和重设计范围，但保留同样信息与求解预算。

专家给正确分解的版本可以做参考上界，不作为主要弱基线。固定参数优化器只用于说明某个局部子空间的性质，不能成为论文胜负的主要依据。

**需要出现的决定性结果：**

- 没有人把正确分工提供给 Agent，它实际构造了新的分工和相应程序。
- 新设计在原完整服务上成立，并且改变确实经过新结构、程序和动态后果实现。
- 禁止关键重构后，优势消失或成本显著上升；允许通用基线相同自由度后，优势仍有实际意义。
- 在不需要重构的控制题中，方法能够保留简单设计，不为展示机制而乱改结构。

**推翻主张的结果：**功能分配由人或候选库提前给出；冻结重构不影响结果；强通用/直接合成在同预算下同样好；优势来自额外仿真或私有事实。这些结果分别表明是工程集成、基础模型能力或预算收益，不能继续用“自主系统设计新机制”包装。

一两个成功轨迹可证明“这条链能运行”，不足以证明稳定优势。后续只补最能区分上述解释的机制实例和独立重复。

## 5. 论文二：从设计经历学会构造下一次的设计问题

### 5.1 为什么不能再只学习 Select

如果 Generate 仍只生成那几套人工方案，Update 仍只识别我们写好的故障类别，那么学习 Select 最多改进既有搜索。它可以有价值，但不是当前希望研究的最核心能力。

第二篇要改的是包含以下步骤的真实 H 程序：

```text
从服务要求和组件事实建立问题表示
从反例提出应重新设计的系统关系
生成新的功能分配与交互实现
把执行后果用于下一次问题构造
```

H 的更新应能让新任务出现不同的设计过程，特别是**产生旧 H 没有生成过的一类有效组合**。这里“一类”需由组件职责与交互结构定义，不能用换一个参数向量冒充。

### 5.2 具体学习对象：产生重构过程的程序

区分三个层次：

| 保存的东西 | 在新任务上做什么 | 支持的结论 |
|---|---|---|
| 一个成功设备方案 | 检索、换参数、再测试 | 设计复用 |
| 一个抽象结构或程序片段 | 重新绑定组件、组合现有片段 | 抽象/程序库复用 |
| 一段修改问题构造过程的程序 | 根据新证据识别应改变的关系，构造新表示和新的设计生成过程 | 设计方法学习的候选 |

第三层也不是天然全新：DreamCoder 的高阶程序学习、HyperAgents 的可编辑改进过程都可能覆盖它。因此必须给出具体学习机制，而不是只把输入输出换名。

### 5.3 拟研究的学习机制：从“修改产生了什么新设计能力”学习 H

输入不是只有最终 PASS/FAIL，而是几次完整的设计改造经历：

```text
原问题表示和原 H 的决策过程
使原分工出问题的执行结果
尝试过但无效的分工/程序修改
成功或部分有效的分工变化、生成过程及完整结果
```

这里需要解决的学习目标，是**什么程序变化让 Agent 获得了构造某类设计的能力**。仅压缩成功程序、记住“加保持组件”、或把成功结果当作补丁信用，都不够。

初版算法可以采用以下具体结构：

1. **提取关系层面的设计变化。** 将不同经历中的具体组件名与数值，映射到它们实际承担的角色、所需资源和时间关系。映射由可执行访问器读取组件属性；不能只靠名称相似。
2. **生成能改写 H 的程序候选。** 候选必须明确修改怎样定位重设计范围、怎样构造功能分配、怎样生成实现中的至少一项。允许联合修改，开发者不规定“这次只许改 Update”。
3. **在开发问题上重新做设计。** 从尚未修好的初始设计开始运行候选 H。评价它是否自己构造了所需关系与新方案，而不是将最终产品答案注入其初态。
4. **用边界反例检验生成能力。** 对训练中的方法候选，用预先允许的机制变化检验它能否重新绑定到不同组件、识别不适用，或提出另一种实现。形成器得到完整后果，在同一有限训练中自主修改代码。
5. **冻结 H，在留出的机制组合上求解。** 开发者不替它补分支。最终评价包含新设计服务、问题构造行为和全部形成成本。

一个拟议的可执行修改，应当像这样工作：

```python
def construct_design_problem(service, components, design, evidence):
    relations = infer_required_producer_consumer_relations(service, evidence)
    for relation in relations:
        if implementation_cannot_realize(relation, design, evidence):
            # 在当前组件中重新寻找承担者及实现方式；不是返回一个旧方案编号。
            alternatives = build_alternative_allocations(relation, components, evidence)
            yield jointly_construct_implementation_problems(alternatives, service)
```

上面是拟议目标形态，**不能由开发者将这段正确逻辑手写给改进组，再称为自动学得**。共同父可有基本的通用实现；真正的更新代码、读取关系与生成行为必须来自形成过程。

### 5.4 它目前最薄弱的地方，必须说透

上述五步仍可能只是“轨迹整理＋LLM 改代码＋测试”。如果最终只有提示组织不同，或只学到一个高阶程序片段，那么与 Trace、DreamCoder、DGM-H 的算法差异仍然不足。

**本篇目前比论文一更不成熟。最需要攻克的技术点，是如何从几次设计改造中学习一个能够构造新改造的程序，而不是将已发生的改造抽象命名。**

建议把具体研究投入集中在“关系层面的改造如何转成可执行的 H 修改”这一处：例如对多个设计变化进行角色对齐，归纳修改前后功能关系必须满足的条件，再合成读取这些关系的代码，并用新绑定下的完整设计后果筛选。角色对齐、程序归纳、试验筛选各自都有先例；需要证明这种组合的特定约束带来可重复收益。

如果最后通用代码改进器同样有效，就应报告通用方法已足够，不能继续把这个组合宣布为新的自改进原理。不能因为要写第二篇，就提前承诺它一定有创新。

### 5.5 什么迁移才配得上这一研究问题

门体案例里，事件与能量可能同时到来，但处理器晚于事件可用。冷链案例里，温度采样义务仍在继续，能量却可能长期消失；恢复后还涉及时钟、历史身份和交付。

真正值得看的不是能否把“门”替换成“箱子”，也不是再调一次储能，而是：

- 新 H 能否根据新的失效关系重新建立功能分工，而不是照搬门体保持方案？
- 它是否知道“数据还在”不意味着“时间仍然正确”，“恢复后补传”不意味着“暗期已经采过样”？
- 对必须持续采样的任务，它是否寻找真实能源与执行安排，而不是靠标记 UNKNOWN 把缺失采样解释成通过？
- 当前组件无法完成服务时，它能否准确保留未解决部分，而不是臆造新组件能力？

这些行为是观察目标，不应逐项写成所提方法的答案清单。测试时给共同组件事实和服务要求，让冻结方法自行推导。

已有 LC 结果参与过开发，不能再称为从 DOOR 到 LC 的零反馈迁移。未来需要按形成前冻结的机制留出定义报告。

### 5.6 最能证明或推翻它的实验

第一项比较不是“新 H 比故意写差的旧 H 好”，而是：

> 相同强父、相同经历、相同代码编辑自由和总资源下，所提形成方法是否更容易产生能构造新设计过程的 H？

至少包括：

- 同历史的强父，不修改程序。
- 通用代码改进方法，允许联合编辑相同函数，例如经过明确适配的 Trace 或 DGM-H 风格实现。
- 所提方法。

经验检索/程序库复用是必要的替代解释控制，可在决定性子实验中加入，不必一开始复制十种方法全矩阵。

**核心检验一：只搬答案是否已经足够。** 将学到的完整 H 与“相同经历＋检索成功设计/程序片段”比较。测试改变组件组合和机制关系，使旧完整方案无法直接复用，但不人为禁用对照的合法重构能力。

**核心检验二：是否真的学会构造新问题。** 在可比设置下清除外部的旧任务状态和具体设计缓存，仅转移各方法允许保存的学习产物；同时保留主比较中相同历史可达的版本。检查新 H 是否实际新建职责关系、生成实现并改变完整服务。基础 LLM 的既有知识无法被清空，因此不能声称这样就证明了“纯粹方法、零知识迁移”。

**核心检验三：所学的重构代码是否必要。** 把该段替换为共同父的实现，其余记忆、工具和预算不变。如果设计过程和结果都不变，所谓方法学习没有成为收益原因。

**核心检验四：生成过程是否稳定。** 重复的是独立形成 H，而不只是把一个优秀 H 多跑几次。少量独立形成即可先判断是否值得继续；正式主张按实际不确定性决定样本量，不用一次成功代替一般优势。

**否证出口：**检索旧片段就同样好；代码变了但新关系没有被读取；只在旧机制上有效；通用改进器同预算同样好；形成成本吞没部署收益。它们分别指向记忆、死代码、专用规则、通用程序搜索或成本问题，不能统一写成“自改进成功”。

## 6. 为什么这次没有为了好测而缩掉核心

| 可以先少做、允许不完善 | 必须真的完成，否则主题已经变了 |
|---|---|
| 只做一个清楚的门体主案例及少量机制变体 | Agent 自己提出至少一种功能分配/交互层面的改造 |
| 仿真组件不覆盖所有真实器件 | 已纳入的组件能力和设计程序真实影响完整执行 |
| 不做实物、采购、制造与物理资格 | 原完整服务不能靠放宽或重命名变成 PASS |
| 不建通用可视化平台、万能知识库或大型多 Agent 系统 | 问题表示与行动生成由实际程序消费 |
| 初期不做 LEAK、不扩十种基线 | 主要对照拥有同样设计自由，不能人为锁死在参数空间 |
| H 不必能改全部代码，G 不必无限递归 | 所学 H 必须改到真正产生设计过程的部分 |
| 初期只验证一种新能力，暂不宣称普遍智能 | 代码更新、行为变化和工程后果之间存在可检验联系 |

研究难度应留在“自主构造系统改造”和“学会更好地构造”上。外围工程可以简化；核心不能由人工代做。

## 7. 现有成果怎样使用，避免重新起炉灶

现有 DOOR 和 LC 的整体方案通过、失败后果、记录与供电轨迹，适合作为组件模型和开发经历。它们证明原环境可以表达有意义的动态服务关系，也揭示了单看电压、接收数量或局部阶段会误导设计。

它们目前没有证明本方案所需的自主功能重新分配，也没有证明从这些经历中学到了新的问题构造程序。不能把人工联合设计换一个标题充当新方法结果。

现有 Generate/Select/Update、形成器和完整仿真可复用，但应检查它们能否表达目标研究对象。如果只能从四套模板挑选，就改掉这一直接限制；不把已有接口视为不可碰的研究边界。需要新增设计原语时，先在待确认方案中明确它改变了什么合法设计空间，再由用户确认；当前不执行。

## 8. 确认后的总管 / A / B 分工建议

以下是建议，**尚未派发**。

| 阶段 | 总管 S0 | A：工程与执行 | B：Agent 方法与论文 | 阶段真正交付 |
|---|---|---|---|---|
| 把核心设计自由落到可执行范围 | 将一项完整服务与允许组合范围固定；所有组共用 | 给出少量组件原语的真实能力、代价及完整执行；明确缺少的最小能力 | 定义可修改的问题构造程序和公平强父，不写入案例修复答案 | 一页问题定义＋一套能表达功能重分配的执行入口 |
| 论文一核心机制 | 运行同条件的完整比较，避免中途救某组 | 独立读回结构/程序改变和完整服务 | 实现反例驱动的范围选择与功能分配算法，分析替代方法 | Agent 形成新分工到真实后果的一条完整链，以及能推翻它的对照 |
| 论文二核心学习 | 固定共同历史、训练与机制留出，完成独立形成比较 | 支持新设计执行及必要的机制结果核对 | 实现从设计变化到 H 修改的学习；对照通用改进与经验复用 | 真正改变问题构造的 H，或明确说明失败发生在哪一步 |
| 写成论文 | 维护结论与结果的一致性，不补无关矩阵 | 整理最必要的模型与复验入口 | 每篇围绕唯一机制写完整论证，不堆阶段增量 | 两个可独立判断贡献是否成立的稿件 |

不把“接口完成”“字段可绑定”“筛选脚本通过”作为等待下一轮审批的独立研究阶段。一次完整实验必须包含方法实际行动和工程后果。但当前处于暂停，任何阶段都须等用户恢复执行。

## 9. 最终研究判断

上一版的约束反演与收益翻转学习，适合作为内部工具，不能保住原来研究主题的中心。

**值得保住的第一步：让 Agent 从系统失败中重新构造功能分配和组件交互，并把它实现出来。**这要求人的问题构造工作真正移交给 Agent。

**值得保住的第二步：让经历改变 Agent 构造下一次设计问题的程序。**这比保存设计、学习动作排序更接近原来的方法自改进目标，也更难。

这两步有研究价值，但价值不自动等于新颖性。第一篇目前有较清楚的可实现算法假设；第二篇的归纳机制仍需要更扎实的技术设计，不能用“高阶”“因果”“递归”替它填空。若最强已有方法已经做到同样效果，应接受该事实，调整贡献定位，而不是继续改名。

我们也不需要先证明一个完美、无所不能的 Agent。需要证明的是：在一个值得做的系统设计问题上，最关键的工作确实由 Agent 完成了；学习后，它确实更会完成同一层次的工作。其余部分围绕这件事做到足够可信即可。
